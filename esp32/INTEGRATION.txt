D100H on ESP32 via BLE

Use a BLE-capable ESP32 (original ESP32, C3, S3, etc.). S2 has no Bluetooth.
The ESP32 is the BLE CENTRAL / GATT CLIENT. It is not a BLE keyboard peripheral.
No USB host hardware is needed for this route. Unplug USB from a computer while
trying BLE on the dual-mode model, since Ulanzi says wired takes priority.

LIVE-VALIDATED ESP32 NOTES (ESP-IDF 5.4.2, NimBLE, ESP32-P4 + ESP32-C6)

This route was validated on hardware. The main ESP-IDF trap is that a
central-only NimBLE build silently discards incoming notifications. Enable both
of these options, even though this device is only a GATT client:

  CONFIG_BT_NIMBLE_ROLE_PERIPHERAL=y
  CONFIG_BT_NIMBLE_GATT_SERVER=y

NimBLE compiles the ATT Notification/Indication opcodes out of its receive
dispatch table when MYNEWT_VAL(BLE_GATTS)=0. The packets still arrive at the
controller and HCI ACL layer, but BLE_GAP_EVENT_NOTIFY_RX never fires. The
device does not need to advertise or accept connections; the GATT-server code
only needs to be linked in.

Send the heartbeat from the NimBLE host task (for example with a
ble_npl_callout) and keep notification callbacks short. On ESP-Hosted,
blocking per-report logging can starve the host task and exhaust the ACL pool.

On the tested unit, HID report 0xFB (handle 69) mirrored the same 20-byte vendor
frame as FD00 (handle 77). Subscribe to FD00 and ignore 0xFB, or de-duplicate,
so one key press produces one action.

Start with Espressif's GATT client example:
https://github.com/espressif/esp-idf/tree/master/examples/bluetooth/bluedroid/ble/gatt_client

1. Put the D100H into pairing mode on a Bluetooth slot, scan and connect.
   Pair/bond if its security requires it; store bonds for reconnection.
   Discover services rather than relying on captured ATT handle numbers.
2. Find service d100h::service_uuid and write/notify characteristics from header.
3. Subscribe to notifications on d100h::notify_uuid (CCCD 0x2902 = 01 00).
4. Send the 20-byte d100h::heartbeat to d100h::write_uuid WITHOUT response
   immediately, and schedule it every 1000 ms while connected.
5. Call d100h::decode(data, length, event) on each vendor notification.
6. Dispatch each event to application logic (GPIO, MQTT, MIDI, etc.).
   Maintain a set of physical held buttons for button+rotation combinations.
   Clear held state and stop heartbeats on disconnect, then reconnect/re-subscribe.

With ESP-IDF Bluedroid use esp_ble_gattc_write_char(..., 20,
heartbeat, ESP_GATT_WRITE_TYPE_NO_RSP, ...), copying the const heartbeat if the
API requires a mutable pointer. Register for notify and enable its CCCD.
Do not perform slow application work inside a BLE callback; queue decoded events.

Application dispatch sketch (include d100h_protocol.h):

  d100h::Event event;
  if (d100h::decode(data, length, event)) {
      switch (event.id) {
      case 0x01: /* top-left, event.down is press/release */ break;
      case 0x02: /* top-middle */ break;
      case 0x03: /* top-right */ break;
      case 0x04: /* upper-left side */ break;
      case 0x05: /* upper-right side */ break;
      case 0x06: /* lower-left side */ break;
      case 0x07: if (event.down) { /* one knob click */ } break;
      case 0x08: /* lower-right side */ break;
      case 0x09: /* counterclockwise step */ break;
      case 0x0a: /* clockwise step */ break;
      case 0x0b: /* counterclockwise with knob held */ break;
      case 0x0c: /* clockwise with knob held */ break;
      }
  }

Knob click is a synthetic down/up pair delivered on physical release in the
captured firmware. Ignore its synthetic up for one-shot actions. Its timing cannot
measure how long the knob was physically held. Turning while pressed uses 0b/0c;
physical side/top buttons still have their own independent transitions.

This is integration guidance and a tested portable codec, not a complete flashed
firmware project. BLE operation has been validated on ESP32-P4 + ESP32-C6;
other ESP32 variants and Bluedroid still need live validation.

Wired USB alternative (also validated on ESP32-P4)

A user confirmed wired D100H FFF1:00DE on macOS: vendor usage page FFFE,
usage 1, unnumbered 64-byte Input and Output reports. The read-only probe was
silent; the active listener's encrypted heartbeat enabled control events.
The descriptor is recorded in tests/fixtures/d100h_wired_usb.json.

For an ESP32 USB implementation, use a USB host-capable board (e.g. S3), a host
stack, and proper 5V VBUS power. Select the vendor interface, send a full encrypted
64-byte heartbeat every second and read 64-byte reports. There is no on-wire
report ID; the leading zero required by desktop HIDAPI is an API convention.
The supplied d100h::heartbeat is the BLE-specific 20-byte value. Do not zero-pad
its ciphertext for USB: pad the heartbeat plaintext to 64 bytes, then encrypt all
eight blocks. d100h::decode_usb() accepts the 64-byte report, or 65 bytes with
the HIDAPI-style leading zero, and decrypts all eight blocks. Only the first
block's padding is validated: the remaining blocks can contain non-zero data on
knob clicks. Do not pass only the first 20 encrypted USB bytes into the BLE
decoder, which leaves its last four bytes unchanged.

The wired path was also validated on an ESP32-P4 USB Host HID implementation
(usage page 0xFFFE, unnumbered 64-byte reports). No complete ESP32 USB host
firmware is supplied here; that is a transport result, not a ready-to-flash
project.
